# Upstart v2.0: what has been decided

A running list of the decisions taken while designing v2.0. The vocabulary is in [GLOSSARY.md](../GLOSSARY.md); the decisions that are hard to reverse have their reasons in [adr/](adr/).

## Product

- For semi-technical makers. Useful for static sites and for dynamic sites and small apps alike.
- Open source under MIT, free, with no account, no team or collaboration features and no plugin system for the app itself. The agent is extended through skills and connectors (see Agent).
- A desktop app. macOS first, signed and notarised; Windows and Linux builds are labelled beta.
- The desktop shell is Electron, chosen on 2026-11-10 after a spike against Electrobun ([ADR 0008](adr/0008-electron-is-the-desktop-shell.md)).
- The app's own interface is React, Tailwind and shadcn/ui, in three columns: a collapsible sidebar listing the projects, the conversation, the preview.
- The preview is a native view inside the window, not an iframe. A second, transparent view above it carries what the interface draws over the preview ([ADR 0008](adr/0008-electron-is-the-desktop-shell.md)).
- The interface is in English only at first, with its texts ready for translation. French follows right after v2.0.
- Projects are created in Documents/Upstart. The maker can pick another folder or open an existing project folder.
- The app updates itself.
- Anonymous usage statistics are sent by default and can be switched off in the settings, with no message at first launch. They are limited to the app version, the operating system, the day's launch, the features used and the type of an error; never a message of the conversation, project content, a file name or a site address. The receiving service is chosen at the polish step, and nothing is sent until then. This was decided knowing that the French and EU texts read on 2026-11-09 call in principle for informing people, and letting them object, before such data leaves their machine.
- No import of projects made with Upstart v1.

## Agent

- Claude at launch, driven through the unmodified official binary. Makers sign in with their subscription through Anthropic's own flow from the first release, and an API key always works instead ([ADR 0002](adr/0002-claude-runs-through-the-unmodified-official-binary.md)).
- Codex is added only if a separate trial, run after the live-generation spike, shows it meets the speed targets. The app is designed for several agents. Gemini is out: its command-line tool no longer serves consumer subscriptions. Reopened on 2026-11-14: other agents and harnesses are to be studied in a spike (see Spikes).
- The agent has a shell, works in auto mode and is confined by the operating system's sandbox ([ADR 0007](adr/0007-agent-has-a-shell-in-auto-mode-inside-the-os-sandbox.md)). Its shell has the system's own tools plus the Node embedded in the app, without npm.
- The agent starts with nothing of the maker's own Claude installation: no connector, skill, plugin, memory or setting of theirs ([ADR 0010](adr/0010-skills-and-connectors-extend-the-agent.md)).
- The agent keeps its configuration, sign-in and conversations in Upstart's own data, never in the maker's Claude folder. A maker already signed in to Claude elsewhere signs in once more inside Upstart, through the binary's own flow or an API key; the agent's conversations never show up in the maker's own Claude.
- Skills extend the agent. Upstart ships its own; the maker adds others for the whole app or for one project, in which case they are kept in the project's folder and travel with it. Skills follow the open Agent Skills format.
- The maker can also add connectors, for the whole app or for one project. A connector's secrets go in the system keychain, never in the project's files.
- A remote connector that asks the maker to sign in (OAuth) is signed in to through the official binary's own sign-in, from a "Sign in…" button by the connector: the binary gives the page to open in the maker's browser and keeps the token itself, never in the project nor in Upstart's own data; on macOS it is in the Keychain, under an item for Upstart's agent data (Q89, 2026-11-11). Tried with Notion's remote server: signed in, its tools were the agent's (Q106, 2026-11-11).
- The sign-in comes back to this computer, where the official binary listens for it for a moment (a loopback return with PKCE, as RFC 8252 advises for desktop apps); a code typed on another device is left out, since neither the binary nor the common services offer it (Q107, 2026-11-11). Each remote connector may instead sign in as an app declared with its service: its identifier, the fixed port it returns to and where the service describes its sign-in, under "Sign-in settings"; Upstart passes them to the binary (Q108, 2026-11-11).
- Skills and connectors are added from the app's settings. The agent can also write a skill into the project when asked.
- A project's skills and remote connectors load without asking. A connector that launches a local program runs outside the sandbox: found in a project, it stays off until the maker approves it once on that machine, the app showing its command.
- One continuous conversation per project. A "start over" button clears the agent's memory without erasing what is displayed.
- A new project is built at once from the maker's first message, optionally from a template. No questionnaire, no mock-up step.
- The agent also answers questions about Upstart itself.
- The site is written in the language of the maker's message unless the maker asks for another (Q88, 2026-11-11), whatever the place or audience the message describes.
- The default Claude model is Sonnet 5.5, which Upstart names explicitly. A small selector in the conversation lets the maker take a faster or a more capable one.
- An effort selector sits next to the model's and shows the levels the chosen model accepts. The setting is kept per project, can be changed at any moment of the conversation, and is medium by default for Claude. It applies to every message, the first one of a new project included.
- The agent can look at the preview (a capture, and the page's errors) to check its own work.
- The agent reads the web, with WebSearch and WebFetch, for every project: a page the maker points to (their current site, a menu online), a fact to check, what well-made sites do now. It takes facts and ideas from it, never another site's texts, images or code; images still come only through find_images or from the maker (Q257, 2026-11-13).

## Live generation

- The maker watches the project being built. Targets: a first visible change within 3 s, a first real section within 10 s, a full home page within 60 s, never a frozen screen.
- The preview leaves its empty state as soon as the theme is being written, showing an empty page in the site's colours before the first text arrives. Measured on 2026-11-10 with medium effort, three builds: the agent's first sentence after 1.4 s, the page in the site's colours after 2.4 to 2.7 s, the first text after 5.1 to 5.7 s, a first complete section after 8.1 to 8.7 s, the full home page after 26 to 33 s. Medium effort does not think before writing: the time goes to writing the theme, then the header.
- The agent writes files, and the app follows what is being written before the files reach the disk: it renders the unfinished file and morphs the preview, for a first build and for later edits alike ([ADR 0009](adr/0009-the-preview-follows-what-the-agent-is-writing.md)). Chosen on 2026-11-10 over two alternatives the spike also measured (instructions applied to the page; files then reload), neither of which is built.
- The agent is instructed to write the theme first, then the home page, then what the home page uses, one file at a time.

## What a project is made of

- A folder of plain files, the sole source of truth ([ADR 0001](adr/0001-project-is-a-folder-of-plain-files.md)).
- The folder holds `theme.css`, the pages under `pages/` (`pages/index.liquid` is `/`, `pages/menu.liquid` is `/menu`), the shared parts under `parts/` and the fragments under `fragments/`. A hidden `.upstart/` folder holds what belongs to the project without being part of the site: its identifier, the chosen model and effort, its skills, and its connectors without their secrets. Datasources are under `data/` and media under `media/` (Q145, Q149).
- Served by one portable, declarative runtime that renders Liquid templates into pages and fragments. The agent writes no server code in v2.0 ([ADR 0003](adr/0003-portable-declarative-runtime.md)).
- Written for htmx 4 ([ADR 0004](adr/0004-projects-are-written-for-htmx-4.md)).
- Datasources are authored (records in project files) or collected (records submitted by visitors, kept in SQLite where the project is published) ([ADR 0005](adr/0005-authored-content-in-files-collected-records-in-sqlite.md)).
- The address of a page follows from where its file is, and one file can produce a page per record (a blog post, a product sheet).
- A datasource is described by a definition file listing its fields and their types. Each datasource gets generated write endpoints, validated against that definition, that answer with HTML fragments.
- In the preview a collected datasource holds test records, which are never published.
- Collected records are read and managed from the app through a token-protected management API of the published runtime.
- No visitor accounts.
- Styled with Tailwind and daisyUI 5, themed through CSS variables: about fifteen core values every project has, plus as many as a project needs. One palette, a dark one only on request ([ADR 0006](adr/0006-tailwind-and-daisyui-themed-through-css-variables.md)).
- Gallery blocks are copied into the project. The gallery's sections are our own, starting from HyperUI's.
- Templates: 30 to 50, made in waves, standard sites and above all original animated designs (Q230, replacing "six to eight polished templates at launch").
- Images come from the maker (media library) or from a keyless search of Openverse and Wikimedia Commons, with licence and attribution kept. No Unsplash, no generated images.

## Datasources and media (build step 3)

- Build step 3 covers authored datasources (definition, records, a page per record, the content editor for them), the media library with image search, and replacing an image in place. Collected datasources, test records, forms and the published records in the content editor are build step 4 (Q144, 2026-11-11).
- An authored datasource is a folder under `data/`: a definition of its fields and one Markdown file per record, its fields at the top and its long text below, as in Astro or Hugo. A record's file name is its id (Q145, 2026-11-11).
- A field is text, long text (Markdown), number, yes/no, date, one choice among a list, image, link, or a list of texts. No references between datasources in v2.0 (Q146, 2026-11-11).
- A page file whose name is a datasource's in brackets, `pages/blog/[posts].liquid`, gives a page per record, at the record's id (`/blog/<id>`); the template sees the record as `record` (Q147, 2026-11-11).
- The content editor is a Content tab beside Theme: the datasources, a datasource's records, a record's form, the preview following each change. A record's text is also edited in place in the preview, as a page's text is (Q148, 2026-11-11).
- Media go in `media/`. An image added is kept in its format but scaled down to at most 2400 px on its longer side; the export also makes smaller sizes and modern formats of each image used (Q149, 2026-11-11).
- The agent searches Openverse and Wikimedia Commons with a tool while building; the maker searches from the media library and from "Replace…" on an image in the preview. Either way the image is copied into `media/` with its licence (Q150, 2026-11-11).
- Search offers only images free for commercial use (CC0, public domain, CC BY, CC BY-SA). Each image's author, licence and source are kept beside it in `media/`, and the runtime writes an "Image credits" line in the site's footer for those that need it (Q151, 2026-11-11).
- A record's fields are YAML between `---` lines at the top of its file; the Markdown below is the field the definition marks as the body, at most one per datasource (Q152, 2026-11-11).
- Records are listed in the order the definition names, a field and a direction (posts by date, newest first). Without one, in a manual order the maker sets by dragging in the content editor, kept in the definition as the list of ids (Q153, 2026-11-11).
- The runtime turns long text into HTML before a template sees it: `{{ record.body }}` shows paragraphs and headings, and `| strip_html | truncate` makes an excerpt (Q154, 2026-11-11).
- An image's alternative text and credits are in a file beside it, `media/cafe.jpg` with `media/cafe.json`, so they travel together (Q155, 2026-11-11).
- For each image a page uses, the export writes WebP copies at 480, 960, 1600 and 2400 px wide, never wider than the image, and gives the page's `<img>` a `srcset` and `sizes`; the original stays as the fallback. The preview shows the originals (Q156, 2026-11-11).
- The credits are a `/credits` page the runtime adds, listing every credited image of the site, with a small "Image credits" link at the end of every footer, while the site has a credited image (Q157 makes Q151's footer line a link, 2026-11-11).
- The media library is in the Content tab, beside the datasources: the project's images as a grid, files dropped in to add them, the search, each image's alt text and credits. The same picker opens from "Replace…" and from an image field (Q158, 2026-11-11).
- In edit mode a selected image shows "Replace…", which opens the media picker; dropping an image file from the Finder onto an image replaces it too. It is an edit by hand, a version in the history with the agent told; an image from a record changes the record's field (Q159 settles Q96, 2026-11-11).
- A datasource's definition is `data/<name>/_datasource.yaml`: its label, its fields (name, kind, required, choices), which field is the body, and the sort or the manual order. A record's id cannot start with an underscore (Q160, 2026-11-11).
- While a datasource is being written, a loop over it shows three stand-in records, shaped by the definition once it is written, until the first record file is complete; then the real records, each as its file completes. No empty moment between them (Q161, 2026-11-11).
- In the Content tab a record is written half a second after typing stops, the preview following; it makes one version in the history, "Edited <record>", when the maker leaves the record, and the agent is told at its next message (Q162, 2026-11-11).
- Only the agent changes a datasource's fields, or creates or deletes a datasource, updating the templates that use them; the Content tab shows the fields and asks the agent. The maker adds, duplicates, deletes and reorders records (Q163, 2026-11-11).
- Each record's page is a page of its own in the preview's address list and in the All pages thumbnails, after the ordinary pages, under a small heading named after the datasource; the right-click menu's Duplicate and Delete act on the record (Q164, 2026-11-11).
- A record added in the Content tab gets an id made from its first text field ("Hello world!" gives `hello-world`), the next free one if taken. The id can be edited, which renames the file and changes the page's address, with a note that links to the old address will break (Q165, 2026-11-11).
- A record whose YAML does not read is left out, with a note the agent sees when it looks at the preview; a missing or wrong value is shown empty. The Content tab marks both on the record, says what is wrong, and offers to ask the agent to fix it (Q166, 2026-11-11).
- That rule stays strict: Upstart does not guess what a header that does not read meant. Right after the agent writes a record or a definition that does not read (with Write, Edit or a command), the tool's answer tells it which file and why, so that it fixes it in the same turn; look_at_preview also lists every datasource's problems, whichever page is shown. The datasources skill lists the YAML pitfalls to avoid: a colon and a space in a text (French spacing included), ` #`, a leading sign, yes/no words, numbers meant as text, commas in list items (Q170, 2026-11-11, after the real "Blog" check left out two posts of three).
- The agent's `find_images` tool returns about ten results as text (title, description, size, licence, author); the agent picks one by its description and calls `use_image`, which copies it into `media/` with its credits and gives its path (Q167, 2026-11-11).
- The media library shows where each file is used ("2 pages, 3 posts"). A file in use cannot be deleted until it is replaced everywhere; one not in use is deleted without confirmation, with an Undo note. Renaming a file updates every page and record that uses it, as one edit by hand (Q168, 2026-11-11).
- The media library holds images (JPEG, PNG, WebP, GIF, AVIF and SVG, which is never resized) and documents to link to (PDF, and any other file dropped in, shown by its name and size). No video or audio players in v2.0: a video is linked or embedded from its host (Q169, 2026-11-11).

## Forms and collected data (build step 4)

- A collected datasource is declared like an authored one, in `data/<name>/_datasource.yaml`, with `collected: true` and its fields; its folder holds no record file (Q171, 2026-11-11).
- In the preview its test records are files in `.upstart/test-records/<name>/<id>.md`, in the format of an authored record: the agent writes them as files, the preview follows them live, snapshots cover them, a form tried in the preview adds one, and no export copies them (Q172, 2026-11-11).
- A form posts to the generated endpoint `POST /_data/<name>` (named so by Q188), which validates what was sent against the definition. When it is valid, the endpoint answers with the fragment the definition names under `answer`, written by the agent, with the new record as `record`; when it is not, with status 422 and a small built-in alert listing the problems, which the form places where it says (`hx-status:422`). The form's own `required` and `type` attributes catch most mistakes first (Q173, 2026-11-11).
- A record a visitor sends appears at once on the pages that show it, unless the definition says `review: true`: then it waits until the maker approves it from the app. The agent sets it for anything shown publicly, such as a guestbook (Q174, 2026-11-11).
- Published on Cloudflare Workers, collected records are stored in D1, Cloudflare's SQLite database bound to the Worker; the guide has the maker create it with one command (Q175, 2026-11-11).
- The Node export stores them with Node's built-in SQLite (`node:sqlite`), in one file beside the app; the guide asks for Node 24 or later (Q176, 2026-11-11).
- From the Content tab, through the management API, the maker lists and opens the records a published site has collected, approves those waiting for review, deletes, and downloads them all as CSV. What a visitor wrote is not edited (Q177, 2026-11-11).
- In a static export, each collected datasource that has a form asks for the address of a form service (the guide names Formspree and Web3Forms); its forms post there as plain forms, and the submissions reach the maker through that service. Left empty, the export warns that the form will not work. A static host runs nothing when a form is sent, so there is no database to download (Q178, 2026-11-11).
- Collected datasources add two kinds of field: e-mail (validated, the form uses `type="email"`) and phone (`type="tel"`, loosely validated since formats vary by country). Visitors cannot upload files in v2.0; an image field in a collected datasource is refused with a note (Q179, 2026-11-11).
- The runtime adds the hidden trap field to every form that posts to `/_data/<name>` when it renders the page, and the endpoint silently drops a submission that fills it; the agent writes nothing for it (Q180, 2026-11-11).
- "Publish" asks every time which builder to use: the static folder, the Node app or the Cloudflare Worker, shown equally with one line each on what it needs and none chosen in advance; static is disabled, saying why, when a page shows collected records. The dialog leaves room for a further destination: Matt plans to sell hosting of his own later, on Cloudflare or on servers (Q181, 2026-11-11).
- When the agent creates a collected datasource that a page displays (a guestbook, reviews), it writes three realistic test records so the layout shows; for one that no page displays (a contact form), none, and the maker tries the form instead (Q182, 2026-11-11).
- The address of the published site is given in the project's settings, whenever the maker wants; the app checks that the site answers with the management token and keeps the address in `.upstart/`, never the token. A new token can be generated there if the old one was lost (Q183, 2026-11-11).
- Nothing is fetched from the published site until the maker opens a collected datasource in the Content tab: no count on opening, no polling, no notification (Q184, 2026-11-11).
- A collected datasource's records are one list in the Content tab: the published records read from the site and the preview's test records, the latter marked as such and editable like authored records; those waiting for review are marked too. The preview always shows the test records only (Q185, 2026-11-11).
- The Node export is one folder: `server.mjs` with the runtime and everything it needs bundled in (no npm install), the site's files and a Dockerfile. The guide covers a server of one's own (systemd behind Caddy) and a platform that runs a Dockerfile; `data.sqlite` sits in a folder the guide says to keep across deployments (Q186, 2026-11-11).
- The button that exports the site is named "Publish" rather than "Put online", and so is its dialog (Q187, 2026-11-12).
- Routes the runtime reserves start with an underscore: `/_data/<name>` for form submissions, `/_upstart/` for the management API. A page file whose name starts with `_` gets no route, with a note for the agent (Q188, 2026-11-12).
- Each builder is a file of its own behind one interface, so that further ones (hosting Matt may sell later) are added without changing the others or the app (2026-11-12, at the step 4 plan).
- The Cloudflare export is a Worker with static assets, configured by `wrangler.jsonc` as Cloudflare now recommends; its compatibility date is the export's, which enables Node compatibility by default (2026-11-12, at the step 4 plan).
- The 422 alert's sentences are written by the agent in the site's language, in the definition (`messages:` with `required`, `invalid` and `too_many`, `{field}` standing for the field's label); a missing one falls back to English. The alert keeps the built-in look (Q189, 2026-11-12).
- What a visitor sends is never read as HTML or Markdown: its texts are escaped, and a long text becomes paragraphs of plain text (2026-11-12, at slice 1).
- A new export into the folder of an earlier one keeps what running or deploying it made: the Node export's `data/` (its SQLite records), `node_modules/`, `.wrangler/`, and the database id the first Cloudflare deploy wrote into `wrangler.jsonc` (2026-11-12, at slice 5).
- The CSV of a collected datasource holds what its list shows: the published records and the test records, with a status column saying published, pending or test; it can be downloaded before any site is published (Q190, 2026-11-12).
- The export writes the website's management token into a `.env` in the exported folder, left out of git and of the Docker image: the Node server reads it, and the Cloudflare export's `npm run deploy` sends it as the Worker's secret (`wrangler deploy --secrets-file .env`). The Publish dialog no longer shows the token or asks to paste it; the website's settings still show it, to replace it (Q191, 2026-11-12).
- Publish remembers, per website on this machine, the way it was last published and each way's folder: the dialog opens with that way chosen, which the maker can change; a website never published has none chosen (Matt, 2026-11-12, after trying step 4).
- A new test record is written when the maker clicks Save, not as they type; an existing one is still saved as it is edited (Matt, 2026-11-12, after trying step 4).
- An export's instructions are its README.md (Matt, 2026-11-12, after trying step 4).
- The Node server counts a visitor by the address the request comes from, or by the first `X-Forwarded-For` address when the request comes from this machine (a reverse proxy such as Caddy in front of it) (2026-11-12, at slice 5).

## The gallery, enlarged (before step 5)

Matt asked on 2026-11-12, once step 4 was built, to enlarge the gallery before the templates, which are made of its blocks.

- The gallery grows from 30 blocks to more than 200, replacing Q92's "about thirty" (Q192, 2026-11-12), in 24 kinds of about nine variants each: header, hero, about, features, services, stats, steps, logos, team, testimonials, gallery, blog, events, menu, products, pricing, comparison, FAQ, contact and hours, forms, newsletter, banner, call to action, footer (Q193, Q196, 2026-11-12).
- A block that lists things is a data block: it brings its datasource's definition and its sample records, and dropping it writes them into the project, where the Content tab edits them. This holds for every repeated list, not only collections: team, blog, events, menu, products, gallery and testimonials, but also questions, features, plans, figures, logos and steps. The forms bring their collected datasource and their answer fragment, as at step 4 (Q194, Q197, 2026-11-12). Blocks other than data blocks keep literal texts; a data block's template holds the Liquid loop over its datasource.
- Data blocks are of two families. A collection keeps one name for the whole site (`team`, `blog`): dropping a block whose collection already exists reuses it, adds to its definition the fields the block needs and writes no sample records (Q198, 2026-11-12). A section list is named after the page it is dropped on (`home-faq`, `services-pricing`), so that two pages never share one by accident (Q201, 2026-11-12).
- Dropping a data block writes the gallery's sample records, three to six, neutral and believable; an empty image field shows a placeholder in theme colours. When the agent uses a block itself, it writes the site's own records instead (Q205, 2026-11-12).
- A list block of a collection with a page per record (blog, events, products) also writes that record page when the project has none. Upstart writes it at once, without the agent, from the frame of the page the block was dropped on: that page's `<head>` and the header and footer parts it renders, with the gallery's detail section between them. An existing record page is kept. The agent is told at its next message, as for anything done by hand (Q199, Q200, 2026-11-12).
- Headers and footers read one site-wide datasource, `navigation`: a record per link with its label, its address, where it shows (header, footer, both, or social) and its own links for a menu, in a new field kind, `links`, a list of label-and-address pairs edited as rows in the Content tab and in place in the preview; footer columns use it too. Its menus open without JavaScript. The records' order is the links' order (Q206, Q208, Q212, 2026-11-12).
- `navigation` is written from the site's pages, home first, when it does not exist yet: for a new site, or when a header or footer block is dropped into an older project. Then the agent adds a link when it creates a page, and the maker edits the links in the Content tab (Q209, 2026-11-12).
- The Content tab lists the collections and `navigation` first, then a Sections group with each page's section lists under that page (Q210, 2026-11-12).
- A section list whose section left its page is kept, marked as used by no page, with a Delete button (Q211, 2026-11-12).
- The Blocks tab keeps its search, with a row of kind chips under it that narrows to one kind; with no chip and no search, the kinds are collapsible groups showing their count (Q204, 2026-11-12).
- Layouts come from several collections under the MIT licence, each rewritten with daisyUI 5 and theme colours, each licence file kept beside the gallery: HyperUI and Meraki UI, maintained, and Mamba UI and Wicked Blocks, older (Tailwind 2) and so more rewritten. Kinds none of them covers well (gallery, events, menu, steps) are written by us (Q195, Q202, 2026-11-12). Checked on 2026-11-12: `Microwawe/mamba-ui` names mambaui.com as its site, under MIT (2020 Mamba UI); `benjaminforras/wickedblocks` names blocks.wickedtemplates.com, under MIT (2021 Michael Andreuzza, its author); both licences are kept beside the gallery. Left out on 2026-11-12, by their licences as read that day: Preline (its Fair Use licence forbids competing products), Flowbite's blocks (their licence could not be read), Float UI, TailGrids and Tailwind Plus (they forbid use in website builders).
- Every block passes an automatic check: one root element, theme colours only, no remote image, its definition and sample records valid, and a render without error under every theme. Each kind also gets a sheet of pictures under three palettes (light, dark, colorful), which Matt reviews batch by batch (Q203, 2026-11-12).
- The agent chooses from metadata and Upstart puts the block in: `find_blocks` answers with what is needed to choose (name, kind, description, mood, tags, and for a data block what it lists and in which family), and a `use_block` tool, one call for a page's sections, puts the chosen blocks into the project the way a drag does, with the same naming of datasources, reuse of a collection, record page from the page's frame and first navigation. The agent then writes this site's texts and records into what was put in (Q213, 2026-11-12).
- `use_block` writes a data block's sample records too, like a drag: the page looks complete at once, and the agent replaces them (Q214, 2026-11-12). Upstart notes in `.upstart/` which records came from the gallery, the record files staying clean, and names to the agent, at the end of its turn, any still unchanged, which it replaces or deletes; Publish says nothing of them (Q217, 2026-11-12).
- A sample the agent rewrote in place keeps the sample's file name, which is its page's address (`/events/acoustic-evening` for a wine evening): at the end of the agent's turn Upstart renames it after its title, its place in the manual order and the links to its old address following. Told to the agent, it still rewrote samples in place in the "Gallery v2" check (Q218, 2026-11-12).
- A record the agent creates itself is named by the agent, after its title in the site's language: the language rule names file names and addresses too. In the fourth "Gallery v2" run it had named 9 of 20 records in French under English titles (`soiree-jazz-et-vin.md` for "Jazz and wine evening"), thinking of a Lyon bistro's dishes in French and writing a file's path before its content; with the rule, the next two runs named every record they created in English. Upstart renames only samples (Q218); renaming the agent's own records stays open if the rule slips (Q219, 2026-11-13).
- The agent's shell returns to the project folder after each command, the instructions tell it to run commands from there without `cd`, and Upstart grants a `cd` joined to a command that writes when it runs in the sandbox and stays in the project, an exception to ADR 0007 (Q220, 2026-11-13). In the "Gallery v2" check such a command was refused for want of anyone to approve it, after an earlier `cd data` had sent its relative paths astray, so the agent could not delete the samples and kept them as six more team members.
- On macOS the agent no longer runs in auto mode: the sandbox alone confines it (a probe showed the home folder and the login keychain out of reach, the network open), so Upstart grants every shell command run in the sandbox, a connector's tool and a skill, writes files in the project and the temporary folder without asking, and refuses the rest. Elsewhere, where commands run unconfined, auto mode stays (Q221, 2026-11-13; ADR 0007).
- A gallery block put into a site, by the agent's use_block or by the maker's drop, shows lorem ipsum in place of the gallery's example texts, each word a lorem word of about its length so the layout holds: its template's texts, its record page's, and its sample records' text, list and Markdown fields. The gallery's example texts read as another business's and looked like a mistake while the agent wrote; a skeleton drawn in the preview was tried and dropped. The Blocks tab keeps the examples, so a block still shows what it is for (Q223, 2026-11-13). Numbers, dates, days, months and times stay with the word joining them, as do web and mail addresses, a form's texts (labels, choices, button), code and drawings, and the site's navigation (Q224).
- The status colors (info, success, warning, error and their text) are derived from the theme's background, with no setting of their own: a fixed hue each, their lightness following the background's, their text near white or near black, whichever reads; a palette changed in the Theme tab carries them along. A page's color scheme (scrollbars, form controls) follows the background's lightness, added where the theme is shown or published, never written into theme.css (Q225, 2026-11-13).
- Beside the roundness, the Theme tab's Shape group sets four style values: Buttons (Square, Like the rest, Pill: the corners of buttons, fields and badges, apart from the roundness), Relief (Flat, Raised), Density (Compact, Normal, Spacious) and Borders (Fine, Bold). Absent from theme.css, each keeps the look a site had before them: buttons like the rest, raised, normal, fine (Q226).
- A palette changes colors only: buttons, relief, density and borders stay as set (Q227).
- The agent may set those four values in theme.css, like the colors; its instructions name them, give their values and say what character calls for each, and to leave them out otherwise. The Theme tab shows what it chose, and a value that is none of the choices selects none (Q228).
- `use_block` takes the page and its blocks in reading order and writes each `{% render %}` line at its place (a banner and a header at the top, a footer at the end), creating the page with the site's frame when it does not exist yet (Q215, 2026-11-12). A part it writes is named by its role, given by the agent (`parts/hero.liquid`, `parts/reviews.liquid`), numbered when taken; a drag keeps the block's id (Q216, 2026-11-12).
- Build order: the machinery first (data blocks and their names, record pages from the copied frame, `navigation` and the `links` field, the Content tab's groups, the Blocks tab, the checks and the sheets), then the 30 existing blocks turned into data blocks where they list things, then the new blocks in six batches of about four kinds, a sheet after each (Q207, 2026-11-12).

## Templates (build step 5)

Designed with Matt from 2026-11-13, once the enlarged gallery was built.

- A maker starts a new website either by describing it or by choosing a template on the start screen, then describing their business: the template is copied into the new project, then the agent adapts it, its texts, images and pages, keeping its design (Q229, 2026-11-13).
- 30 to 50 templates in all, made in waves, replacing the earlier "six to eight at launch". Besides standard sites, and above all, original designs, inventive and animated, in the spirit of what Awwwards, Siteinspire, Dribbble, Behance and Land-book show: inspired by their trends, never a copy of a particular site (Q230). The first wave has eight: four standard (local business, portfolio, blog, launch page) and four original animated designs (Q244).
- A template's images are real, openly licensed images (Openverse, Wikimedia Commons), copied into the project with their credits; the agent replaces them while adapting (Q231).
- Templates are made here, with a template-making skill written first: an Upstart skill, used in development to make ours and later by outside template authors. A template brings its own blocks (Q232, Q240).
- On disk a template is an ordinary Upstart project folder plus a template.json (its name, description, pictures, category, scripts, licences and credits) and its blocks in blocks/, in the gallery's format. An author opens it in Upstart to see it and change it with the agent (Q240).
- A template animates with CSS and with JavaScript libraries (Q233). GSAP is left out: its licence forbids tools competing with Webflow, which a website builder is.
- A template has a stylesheet of its own for its effects, type and bold layouts, but its colors, fonts and roundness still come from the theme, so the Theme tab still changes the whole site and gallery blocks still fit it (Q234; ADR 0006).
- A template's blocks are copied into the project, and the Blocks tab shows them first, in a group for this design, to add a section in the same style; the shared gallery follows (Q235).
- An outside author's template is a folder or a .zip the maker imports from the start screen; an online catalogue comes later (Q236).
- A template declares its scripts in its manifest and Upstart loads them, in the preview and once published, calling their start function on load, after each htmx swap and after each preview update; pages hold no script tags (Q237).
- Upstart offers a checked list of openly licensed libraries, to which an author may add any library, given by its address or shipped in the template, plus the template's own start script (Q238). A library given by its address is loaded from there on every visit, in the preview and once published, not copied into the project (Q241), chosen knowing that the site then depends on that server and that visitors' addresses reach it.
- A template brings design notes for the agent, a skill copied into the project: its spirit, its effects and how to use them, what not to break. The agent may also write new JavaScript (Q239).
- In edit mode the preview shows the page in its final state, with no scripts and no animations, so that selecting, moving and editing texts work on the real HTML; in visitor mode and once published, everything moves (Q242).
- The preview opens in visitor mode, so the maker sees the site move as visitors will; edit mode is one click away (Q253, 2026-11-13, Matt's correction: edit mode was the default). Each site opens so, the mode chosen lasting only while the site is open (Q255). A block dragged from the Blocks tab, or an image file from the Finder, into the page puts the preview in edit mode by itself, and it stays there (Q254).
- A template's blocks may overlap, tilt and stack where the design calls for it, provided they stay readable and clean on a phone; the shared gallery keeps its rule that nothing floats over the rest (Q256).
- Comment mode is still too, as edit mode is: the page runs none of the site's scripts there (2026-11-13, building slice 1).
- A site's JavaScript, from a template or the agent, lives in scripts/ ([ADR 0011](adr/0011-sites-carry-javascript-loaded-by-upstart.md)): libraries in scripts/lib/, the site's own code in scripts/*.js, modules exporting a start function that Upstart loads and calls; the same for every site, with or without a template (Q243).
- Starting a new website, the window shows the sidebar and one large panel: the optional templates to start from, and the message box at the bottom center. Once the first message is sent, the window takes its usual layout (Q245, 2026-11-13). In that panel thumbnails move on hover, a click selects a template, View opens it large, real and animated, its pages browsable, the message box still below; category chips filter the grid, and Import a template is there too (Q249).
- Adapting a template, the agent rewrites every text and record for the maker's business, replaces the images, adds or removes pages as the description asks, and keeps the design and its effects; at the end Upstart checks that no text of the template is left, as for lorem ipsum (Q246).
- The app ships only the templates' list and thumbnails; a template is downloaded when the maker views it large or chooses it (Q247), from a public GitHub repository of Upstart's templates, [upstart-gg/upstart-templates](https://github.com/upstart-gg/upstart-templates) (created 2026-11-13; upstart-gg/templates is the old Upstart's and stays as it is, Matt), each release publishing a catalogue and one .zip per template (Q250).
- The public repository holds the templates' sources; its CI builds each release from them on a tag (the catalogue, the pictures and one .zip per template, attached to the GitHub release), so the .zip files are never committed (Q265, Matt, 2026-11-13).
- As built (2026-11-13, templates slice 9): a packaged app reads `<releases>/latest/download/catalogue.json` at its start (keeping the last one read for the next start, offline), shows the pictures it ships (`apps/desktop/templates-catalogue`, taken by `pnpm template:snapshot` when it is packaged) or downloads those of a newer release, and downloads a template's .zip (without its pictures) into its cache when it is viewed large or chosen, refusing one whose size or sha256 differs from the catalogue's; offline, the large view and the first message say the template could not be downloaded, and starting from scratch stays possible. In development the templates are read from `apps/desktop/templates` (or from a release with UPSTART_TEMPLATES_URL). `pnpm template:release` builds a release here as the CI does; its CI runs the app's own checks, bundled to run with Node alone (`pnpm template:release-script`).
- The templates' only source is upstart-gg/upstart-templates; Upstart's repository has it as a git submodule at `apps/desktop/templates`, pinned to a commit, which development and the tests read; a template is made and committed there, then released by a tag (Q267, Matt, 2026-11-14). The format moved to the templates repository's `FORMAT.md`.
- Importing an outside template shows its name and its pictures before it is accepted, not its scripts (Q248).
- In time, the makers themselves propose templates: made in the app, and submitted by pull request to upstart-gg/upstart-templates, a GitHub account being asked of template creators (Matt, 2026-11-14). It is a step of its own, designed later; templates slice 10 checks only a website started from a template, with the real agent (Q266).
- As checked (2026-11-14, templates slice 10, `e2e/agent-template.e2e.ts`, the real agent in the packaged app, each template downloaded from the latest release): Reel for a ceramics studio in Lisbon, in English, and Corner for a cheese shop in Toulouse, in French, came out rewritten (none of the template's sentences or invented business left, the Stop hook naming three leftovers once in Reel's run), their images replaced and credited, theme, scripts and effects unchanged, every page linked, in the maker's language, in two to three minutes each. The French labels ran into Corner's order button at tablet width, and the agent had not looked at its pages: the adaptation instruction now has it look at each page and fix what the new texts broke (look_at_preview takes a page's address, the preview going there first; looks asked at once run one after another, since a capture taken while the preview moves never ends), the making-templates skill asks for headers that hold labels a third longer, and Corner 1.0.1 (release v2) shows its links from 1024 px. Every header was then measured at 768 to 1280 px with French labels: Margin's labels wrapped, Marquee's order button left the screen and Pocket's last link ran into its button below 1024 px, so Margin, Marquee and Pocket 1.0.1 (release v3) show their links from 1024 px too, on one line; Folio's held (2026-11-14, Matt).
- As found (2026-11-14, Matt's site started from Pocket in the dev window): the home page stayed blank in the preview once the agent had written it, the glow's WebGL raising errors. After each new rendering the preview called each module's stop on the page the rendering had already replaced, then start on the same elements: Motion remembers the last value it set, so a reveal animating to opacity 1 saw nothing to do and left its text hidden (in six of the eight templates); Pocket's glow had lost its WebGL context in stop, on a canvas that starts again; its phone story could not put its screens back. The preview now stops the modules before a rendering takes the page's place and starts them once it is complete (ADR 0011); every hidden start value is given (opacity: [0, 1]) and the glow keeps its context: Beacon, Ember and Folio 1.0.1, Corner, Margin and Pocket 1.0.2 (release v4). `e2e/templates-again.e2e.ts` renders each page of a template again twice at desktop and phone width and fails on anything left hidden or any error (Pocket by default, UPSTART_TEMPLATE=all for the eight, and in `pnpm template:shoot`); the site-scripts skill gives the rule to the agent.
- A template starts a website; an existing site does not change template in v2.0. Its style changes through the Theme tab, the blocks or the agent (Q251).
- The template-making skill has the agent study current trends first (Awwwards, Siteinspire, Land-book and the like, as inspiration only), write a design brief (concept, type, palette, motion, pages) the author approves, then build, check and photograph the template (Q252).
- As built (2026-11-13, templates slice 3): the manifest holds what the start screen shows (id, version, name, description, a category among business, portfolio, blog, launch, event and app, `original` for the original designs, tags, author, licence); what the project's files already say (the libraries' licences, the images' credits, the pictures) is not repeated in it but read from them. Making one in the app, for outside authors, comes with the public templates repository (Q258, 2026-11-13).
- Wave 1's six remaining templates were briefed together (2026-11-13, approved together): Margin (blog), Beacon (launch page), Marquee (festival, original), Pocket (app, original), Ember (evening wine bar, original) and Reel (creative studio, original), in `docs/template-briefs/`. ## Editing

- In the preview: inline text editing, comments on elements sent to the agent (see below), a responsive view, and direct actions on the selected element (replace image, change link, duplicate, delete). No inspector panel.
- Editing in place a text that comes from a record or from a shared part changes the source, so everywhere that text appears. A marker says so before the maker types.
- Drag and drop covers dropping a gallery block into a page and reordering a page's sections. Anything finer goes through the agent.
- What the maker does by hand in the preview (a text typed in place, a duplicated, deleted or moved section, a dropped block) is written into the project's files by the app itself, not by the agent; the agent is told at its next message what the maker changed. A text computed by a Liquid expression cannot be edited in place: the app offers to ask the agent (Q90, 2026-11-11).
- Editing by hand is paused while the agent works, the stop button staying at hand (Q91, 2026-11-11).
- Each action by hand is its own snapshot, so it can be undone alone; keystrokes in the same text make one. In the timeline, several actions by hand in a row are folded into one collapsible entry so they take little room by default (Q94, 2026-11-11).
- Talking to the agent about the page goes through comments, which take the place of selecting one element. The maker turns on commenting with a button, clicks an element, writes in a card that opens on it, and can do so on several elements; a send button in a toolbar floating on the page (or in the preview's own toolbar where a floating one does not fit) sends them all as one message in the conversation, each with the element it is about (Q95, 2026-11-11). The cards and the floating toolbar are drawn by the editing script inside the preview, as ADR 0008 foresees for what points into the page.
- Replacing an image directly waits for the media library at build step 3; until then the maker asks the agent (Q96, 2026-11-11; settled by Q159).
- The block gallery and the theme editor open as tabs of the middle column, beside the conversation; the preview stays whole and a block is dragged from the column into the page (Q100, 2026-11-11).
- A block dropped into a page becomes a shared part of its own under `parts/`, included by the page where it was dropped, so it can be used on other pages as well (Q101, 2026-11-11). The agent keeps writing its own sections inside the page's file, and makes a section a shared part only when several pages use it (a header, a footer) or when it starts from a gallery block (Q102, 2026-11-11).

A button in the preview's toolbar switches to a visitor's view, where links, buttons and htmx behave as they will online (Q99, 2026-11-11). The preview now opens in that visitor's view (Q253).

The search is by keywords and tags with synonyms; a search by meaning can be added later behind the same tool (Q97 and Q98, 2026-11-11).

Sections particular to the business are still its own (Q104, 2026-11-11).
- After the page, the agent writes the hero's part first, then the other parts in reading order, so the first text the maker sees is the hero's rather than the header's (Q105, 2026-11-11).
- A block goes into a page by dragging it there, the line showing where; the cards have no Add button. The Blocks tab has a search bar that narrows the blocks as one types, in English or French (Q112, 2026-11-11).
- The Theme tab's first palette is "Site's own": the colours the agent first wrote for the website, chosen when nothing else is (Q113, 2026-11-11).
- "Site's own" changes when a colour is edited while it is the palette shown; edited from another palette, it stays as it was. The twelve ready-made palettes never change. It is kept in Upstart's data for the project, not in the website, and going back in the history does not change it (Q114, 2026-11-11).
- Settings are drawn in Upstart's own look, mocked up as several directions on a canvas before choosing (Q115, 2026-11-11).
- Settings open in a window of their own (⌘,), laid out like macOS System Settings: a sidebar with a search field, the Claude account at its top and a coloured icon per category; on the right, the category's page in grouped rows, the label on the left and the control on the right (Q116, 2026-11-11).
- Six categories: General (the websites' folder, appearance), Agent (the account; the model and effort for new websites), Skills, Connectors, Privacy (the anonymous statistics), About Upstart (Q117, 2026-11-11).

Each website has its own settings, opened from a button on its row in the websites list: its model and effort, its own skills and connectors, kept in its folder; they also say which connectors it gets from Settings (Q118, 2026-11-11). The canvas's first ideas, a switch on each page or a "This website" category, were turned down.

## Publishing

- Three builders: static folder, Node app, Cloudflare Worker. Each produces a ready-to-deploy folder and a step-by-step guide. The maker deploys, then gives the app the project's address. No one-click publishing in v2.0.
- In a static export a form posts to a third-party form service chosen by the maker. A project with a page that displays collected records cannot be exported statically.
- For a Node or Cloudflare export the app generates the management token, the guide says where to set it at the host, and the app keeps it in the system keychain.
- The agent writes a title, a description and sharing tags in every page.
- Forms get a hidden trap field and a per-visitor rate limit. No captcha.
- Fonts are copied into the project, or loaded from a CDN as long as rendering does not suffer. JavaScript and CSS libraries may come from a CDN. The Tailwind stylesheet is compiled at export.
