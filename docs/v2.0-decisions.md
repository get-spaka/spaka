# Upstart v2.0: what has been decided

A running list of the decisions taken while designing v2.0. The vocabulary is in [GLOSSARY.md](../GLOSSARY.md); the decisions that are hard to reverse have their reasons in [adr/](adr/).

## Product

- For semi-technical makers. Useful for static sites and for dynamic sites and small apps alike.
- Open source under MIT, free, with no account, no team or collaboration features and no plugin system for the app itself. The agent is extended through skills and connectors (see Agent).
- A desktop app. macOS first, signed and notarised; Windows and Linux builds are labelled beta.
- The desktop shell is Electron, chosen on 2026-11-10 after a spike against Electrobun ([ADR 0008](adr/0008-electron-is-the-desktop-shell.md)).
- The app's own interface is React, Tailwind and shadcn/ui, in three columns: a collapsible sidebar listing the projects, the conversation, the preview.
- The preview is a native view inside the window, not an iframe. A second, transparent view above it carries what the interface draws over the preview ([ADR 0008](adr/0008-electron-is-the-desktop-shell.md)).
- The interface is in English only at first, with its texts ready for translation. French follows right after v2.0.
- Projects are created in Documents/Upstart. The maker can pick another folder or open an existing project folder.
- The app updates itself.
- Anonymous usage statistics are sent by default and can be switched off in the settings, with no message at first launch. They are limited to the app version, the operating system, the day's launch, the features used and the type of an error; never a message of the conversation, project content, a file name or a site address. The receiving service is chosen at the polish step, and nothing is sent until then. This was decided knowing that the French and EU texts read on 2026-11-09 call in principle for informing people, and letting them object, before such data leaves their machine.
- No import of projects made with Upstart v1.

## Agent

- Claude at launch, driven through the unmodified official binary. Makers sign in with their subscription through Anthropic's own flow from the first release, and an API key always works instead ([ADR 0002](adr/0002-claude-runs-through-the-unmodified-official-binary.md)).
- Codex is added only if a separate trial, run after the live-generation spike, shows it meets the speed targets. The app is designed for several agents. Gemini is out: its command-line tool no longer serves consumer subscriptions.
- The agent has a shell, works in auto mode and is confined by the operating system's sandbox ([ADR 0007](adr/0007-agent-has-a-shell-in-auto-mode-inside-the-os-sandbox.md)). Its shell has the system's own tools plus the Node embedded in the app, without npm.
- The agent starts with nothing of the maker's own Claude installation: no connector, skill, plugin, memory or setting of theirs ([ADR 0010](adr/0010-skills-and-connectors-extend-the-agent.md)).
- The agent keeps its configuration, sign-in and conversations in Upstart's own data, never in the maker's Claude folder. A maker already signed in to Claude elsewhere signs in once more inside Upstart, through the binary's own flow or an API key; the agent's conversations never show up in the maker's own Claude.
- Skills extend the agent. Upstart ships its own; the maker adds others for the whole app or for one project, in which case they are kept in the project's folder and travel with it. Skills follow the open Agent Skills format.
- The maker can also add connectors, for the whole app or for one project. A connector's secrets go in the system keychain, never in the project's files.
- A remote connector that asks the maker to sign in (OAuth) is signed in to through the official binary's own sign-in, from a "Sign in…" button by the connector: the binary gives the page to open in the maker's browser and keeps the token itself, never in the project nor in Upstart's own data; on macOS it is in the Keychain, under an item for Upstart's agent data (Q89, 2026-11-11). Tried with Notion's remote server: signed in, its tools were the agent's (Q106, 2026-11-11).
- Skills and connectors are added from the app's settings. The agent can also write a skill into the project when asked.
- A project's skills and remote connectors load without asking. A connector that launches a local program runs outside the sandbox: found in a project, it stays off until the maker approves it once on that machine, the app showing its command.
- One continuous conversation per project. A "start over" button clears the agent's memory without erasing what is displayed.
- A new project is built at once from the maker's first message, optionally from a template. No questionnaire, no mock-up step.
- The agent also answers questions about Upstart itself.
- The site is written in the language of the maker's message unless the maker asks for another (Q88, 2026-11-11), whatever the place or audience the message describes.
- The default Claude model is Sonnet 5.5, which Upstart names explicitly. A small selector in the conversation lets the maker take a faster or a more capable one.
- An effort selector sits next to the model's and shows the levels the chosen model accepts. The setting is kept per project, can be changed at any moment of the conversation, and is medium by default for Claude. It applies to every message, the first one of a new project included.
- The agent can look at the preview (a capture, and the page's errors) to check its own work.

## Live generation

- The maker watches the project being built. Targets: a first visible change within 3 s, a first real section within 10 s, a full home page within 60 s, never a frozen screen.
- The preview leaves its empty state as soon as the theme is being written, showing an empty page in the site's colours before the first text arrives. Measured on 2026-11-10 with medium effort, three builds: the agent's first sentence after 1.4 s, the page in the site's colours after 2.4 to 2.7 s, the first text after 5.1 to 5.7 s, a first complete section after 8.1 to 8.7 s, the full home page after 26 to 33 s. Medium effort does not think before writing: the time goes to writing the theme, then the header.
- The agent writes files, and the app follows what is being written before the files reach the disk: it renders the unfinished file and morphs the preview, for a first build and for later edits alike ([ADR 0009](adr/0009-the-preview-follows-what-the-agent-is-writing.md)). Chosen on 2026-11-10 over two alternatives the spike also measured (instructions applied to the page; files then reload), neither of which is built.
- The agent is instructed to write the theme first, then the home page, then what the home page uses, one file at a time.

## What a project is made of

- A folder of plain files, the sole source of truth ([ADR 0001](adr/0001-project-is-a-folder-of-plain-files.md)).
- The folder holds `theme.css`, the pages under `pages/` (`pages/index.liquid` is `/`, `pages/menu.liquid` is `/menu`), the shared parts under `parts/` and the fragments under `fragments/`. A hidden `.upstart/` folder holds what belongs to the project without being part of the site: its identifier, the chosen model and effort, its skills, and its connectors without their secrets. The folders for datasources and media are confirmed at build step 3.
- Served by one portable, declarative runtime that renders Liquid templates into pages and fragments. The agent writes no server code in v2.0 ([ADR 0003](adr/0003-portable-declarative-runtime.md)).
- Written for htmx 4 ([ADR 0004](adr/0004-projects-are-written-for-htmx-4.md)).
- Datasources are authored (records in project files) or collected (records submitted by visitors, kept in SQLite where the project is published) ([ADR 0005](adr/0005-authored-content-in-files-collected-records-in-sqlite.md)).
- The address of a page follows from where its file is, and one file can produce a page per record (a blog post, a product sheet).
- A datasource is described by a definition file listing its fields and their types. Each datasource gets generated write endpoints, validated against that definition, that answer with HTML fragments.
- In the preview a collected datasource holds test records, which are never published.
- Collected records are read and managed from the app through a token-protected management API of the published runtime.
- No visitor accounts.
- Styled with Tailwind and daisyUI 5, themed through CSS variables: about fifteen core values every project has, plus as many as a project needs. One palette, a dark one only on request ([ADR 0006](adr/0006-tailwind-and-daisyui-themed-through-css-variables.md)).
- Gallery blocks are copied into the project. The gallery's sections are our own, starting from HyperUI's.
- Six to eight polished templates at launch: launch page, portfolio, local business, blog, event, small app with a datasource and a form.
- Images come from the maker (media library) or from a keyless search of Openverse and Wikimedia Commons, with licence and attribution kept. No Unsplash, no generated images.

## Editing

- In the preview: inline text editing, comments on elements sent to the agent (see below), a responsive view, and direct actions on the selected element (replace image, change link, duplicate, delete). No inspector panel.
- Editing in place a text that comes from a record or from a shared part changes the source, so everywhere that text appears. A marker says so before the maker types.
- Drag and drop covers dropping a gallery block into a page and reordering a page's sections. Anything finer goes through the agent.
- What the maker does by hand in the preview (a text typed in place, a duplicated, deleted or moved section, a dropped block) is written into the project's files by the app itself, not by the agent; the agent is told at its next message what the maker changed. A text computed by a Liquid expression cannot be edited in place: the app offers to ask the agent (Q90, 2026-11-11).
- Editing by hand is paused while the agent works, the stop button staying at hand (Q91, 2026-11-11).
- Each action by hand is its own snapshot, so it can be undone alone; keystrokes in the same text make one. In the timeline, several actions by hand in a row are folded into one collapsible entry so they take little room by default (Q94, 2026-11-11).
- Talking to the agent about the page goes through comments, which take the place of selecting one element. The maker turns on commenting with a button, clicks an element, writes in a card that opens on it, and can do so on several elements; a send button in a toolbar floating on the page (or in the preview's own toolbar where a floating one does not fit) sends them all as one message in the conversation, each with the element it is about (Q95, 2026-11-11). The cards and the floating toolbar are drawn by the editing script inside the preview, as ADR 0008 foresees for what points into the page.
- Replacing an image directly waits for the media library at build step 3; until then the maker asks the agent (Q96, 2026-11-11).
- The block gallery and the theme editor open as tabs of the middle column, beside the conversation; the preview stays whole and a block is dragged from the column into the page (Q100, 2026-11-11).
- A block dropped into a page becomes a shared part of its own under `parts/`, included by the page where it was dropped, so it can be used on other pages as well (Q101, 2026-11-11). The agent keeps writing its own sections inside the page's file, and makes a section a shared part only when several pages use it (a header, a footer) or when it starts from a gallery block (Q102, 2026-11-11).
- Duplicating a section that is a shared part makes an independent copy, a new part the maker can change without touching the original (Q103, 2026-11-11).
- In the preview a click selects an element (an outline and a small bar of actions) and a double click on a text edits it in place. A button in the preview's toolbar switches to a visitor's view, where links, buttons and htmx behave as they will online (Q99, 2026-11-11).
- The agent uses the gallery too, through a tool of Upstart's own that searches the blocks by kind, words and mood and returns the few best with their code, so nothing grows in the agent's context as the gallery grows; a short skill says when to use it. The search is by keywords and tags with synonyms; a search by meaning can be added later behind the same tool (Q97 and Q98, 2026-11-11).
- On a new page the agent starts from the gallery before writing the page: it looks for blocks for the page's common sections first, then writes the page, taking those sections from the blocks it found, as shared parts with the project's own texts. Sections particular to the business are still its own (Q104, 2026-11-11).
- After the page, the agent writes the hero's part first, then the other parts in reading order, so the first text the maker sees is the hero's rather than the header's (Q105, 2026-11-11).
- The gallery at build step 2 holds about thirty blocks: three or four variants for each of eight kinds (header, hero, features, testimonials, pricing, questions, call to action, footer), written by us from HyperUI's with the theme's colours (Q92, 2026-11-11).
- The theme editor offers a dozen ready palettes applied in one click, each colour adjustable, a choice of fonts (system fonts and a selection from Google Fonts) and the corner radius, the page following live. A dark palette, on request, is made by the agent (Q93, 2026-11-11).
- A content editor (a table of records, for local and published data) and a media library.
- History is a single line of snapshots with undo and a timeline, kept by the app without touching the maker's own git repository. The snapshots live in the app's own data, outside the project folder and tied to the project by its identifier: the agent can neither read nor damage them, and a project that is copied or received starts without its history.
- Attachments in the conversation.
- Help: a five-step tour on the first project, a tooltip on every button, and the agent's own answers.

## Publishing

- Three builders: static folder, Node app, Cloudflare Worker. Each produces a ready-to-deploy folder and a step-by-step guide. The maker deploys, then gives the app the project's address. No one-click publishing in v2.0.
- In a static export a form posts to a third-party form service chosen by the maker. A project with a page that displays collected records cannot be exported statically.
- For a Node or Cloudflare export the app generates the management token, the guide says where to set it at the host, and the app keeps it in the system keychain.
- The agent writes a title, a description and sharing tags in every page.
- Forms get a hidden trap field and a per-visitor rate limit. No captcha.
- Fonts are copied into the project, or loaded from a CDN as long as rendering does not suffer. JavaScript and CSS libraries may come from a CDN. The Tailwind stylesheet is compiled at export.

## Building it

- The repository is private and local for now, with no remote. Work is committed on `main` as it goes: one commit for the documents and the spikes, then one per slice that works.
- Code, comments, documentation, glossary and ADRs are in English.
- The design was confirmed on 2026-11-09. A new design question reopens this list before anything is built on it. It was reopened on 2026-11-10 for the effort setting, skills and connectors.
- Two throwaway spikes came first, each ending with a short report of measurements and a written decision. Both reported on 2026-11-10. The app is then written from scratch.
- The message to Anthropic about subscription sign-in ([ADR 0002](adr/0002-claude-runs-through-the-unmodified-official-binary.md)) is written later, before the first version is distributed.
- Build order, each step leaving a usable app: (1) conversation, live preview, history, static export, the effort selector, skills and connectors; (2) visual editing, gallery, theme; (3) datasources, content editor, media; (4) forms, Node and Cloudflare exports; (5) templates, tour, polish.

## Spikes, run before building

Their full framing and outcomes are in [spikes.md](spikes.md).

- **Live generation**, with Claude only. Done, see the [report](../spikes/live-generation/REPORT.md): the preview follows what the agent is writing (ADR 0009); Liquid, htmx 4 without the compatibility extension, and the theme's variables are confirmed (ADRs 0003, 0004, 0006); the agent's confinement holds on macOS and a blocked action is refused without asking (ADR 0007).
- **Desktop shell**, Electron against Electrobun. Done, see the [report](../spikes/desktop-shell/REPORT.md): Electron, with the preview as a native view (ADR 0008).

## Not verified yet

- Under an API key: the stream the live preview rests on, and what auto mode costs in tokens.
- On Windows and Linux: the agent's confinement, the preview's rendering, and everything about the native view.
- A bubble drawn over the preview that follows an element while the page scrolls or the window is resized.
- The agent in a signed and notarised app, and auto-update in practice.
- htmx 4 beyond what a form needs.
- How auto mode judges a call to a connector's tool that has effects elsewhere (a call that only reads was allowed).
- What only a person can judge in a visible window: how resizing feels, scrolling the preview with a trackpad, the step-1 app used for real.
- A static export put online at one of the hosts the guide names (it is checked served from a local folder only), and a fragment that reads its parameters in a static site.

## Deferred beyond v2.0

One-click publishing and hosting; custom server code; JSON answers from endpoints; visitor accounts; multilingual projects; external data sources; an inspector panel; dragging elements inside a section; an SEO settings panel with sitemap.xml and robots.txt; e-mail on form submission; visit statistics; voice dictation; a French interface; captcha on forms.
